BELM PORTAL V265 - FIX: "SERVER ERROR" ON RECOMMEND SPARE (AND ANNOUNCEMENTS)

ROOT CAUSE (confirmed real bug)
- log_activity() is declared as `function log_activity(array $user, ...)`
  - it expects the FULL user/staff array (it reads $user['id'] itself
  internally), not just an ID string.
- backend/api/spare_recommendations.php was calling it as
  log_activity($payload['id'], ...) - passing a plain string where an
  array was required. PHP throws a TypeError for this, which is an
  uncaught crash -> the generic "Server error. Check the API error log
  and database configuration." message shown in the screenshot.
- Critically, this crash happened AFTER the recommendation was already
  fully saved (the service_requests / service_request_parts /
  service_request_history inserts all committed successfully just
  before the crashing line). So "Recommend Spare to Customer" was
  actually WORKING and saving data - it just crashed right at the very
  end, before it could tell the Technician it succeeded. Retrying after
  seeing this error would have created duplicate recommendations for
  the same spare part.

- The exact same mistake existed in backend/api/announcements.php in
  two places (create and delete an admin announcement) - same crash-
  after-success pattern there too.

FIXED
- backend/api/spare_recommendations.php: now passes the full $payload
  array to log_activity(), matching its actual signature.
- backend/api/announcements.php: same fix in both the create and
  delete handlers (now passes $user instead of $user['id']).
- Checked every other log_activity(...) call site in the codebase
  (users.php, customers.php, billing.php, proforma_invoices.php,
  spare_parts.php, checklist_templates.php, engineering.php,
  suppliers.php, controller_pinouts.php, company_expenses.php,
  bank_manager.php) - all of those were already calling it correctly.

- No frontend files changed, so no cache bump needed.
- No database migration required.
