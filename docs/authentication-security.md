# Authentication security migration

BELM now uses an 8-hour rolling `HttpOnly`, `SameSite=Lax` cookie for browser sessions. Login, legacy login, operator login, and refresh still return a bearer token for older screens, but that compatibility token expires after 15 minutes instead of 30 days. Existing frontend code can therefore migrate page-by-page without breaking current role, customer, technician, recovery, or refresh flows.

## Request flow

1. A successful login verifies the existing bcrypt password and issues both the browser cookie and a 15-minute compatibility token.
2. API authentication accepts a valid bearer token first, then the HttpOnly cookie. Cookie-authenticated state-changing requests are limited to configured origins.
3. Refresh re-checks the live account and rotates both credentials.
4. Logout clears the cookie and increments the account session generation. Password reset and recovery also increment that generation, invalidating newly issued sessions on every device.
5. Direct downloads request `POST /api/auth/download-token` with `{"path":"/api/.../download"}`. The returned URL contains a purpose-bound `download_token` valid for at most two minutes and only for the exact GET path. General session JWTs in `?token=` are no longer accepted.

## Frontend migration

New or updated screens should use `credentials: "include"` and must not require the response `token`. During the compatibility period, older screens may keep the short token in `localStorage`; the shared session runtime refreshes it shortly before expiry. Once all screens use cookies, remove the token response and legacy Authorization headers.

Explicit logout should call `POST /api/auth/logout`. The shared theme runtime captures existing logout controls and sends this request before redirecting.

## Secrets and deployment

No secret is committed. JWT signing continues to use `JWT_SECRET`, generated by Render. Database and bootstrap credentials remain environment-only. Deploy the schema change before or with the application code so `auth_session_versions` is available; the code fails open only for session-version lookup errors to avoid locking out all users during a rolling deploy, and logs that condition for operators.

## Risks to monitor

- Old, unversioned JWTs remain valid until their original expiry for compatibility. Normal refresh upgrades them to versioned short tokens; a later hard-cutover can reject missing `sv` claims.
- `SameSite=Lax` is appropriate for the current same-site portal. If the frontend moves to a different registrable domain, cookie policy and CSRF controls must be revisited.
- Any legacy direct link still using `?token=<main JWT>` now receives 401 and must first call the download-token endpoint.
